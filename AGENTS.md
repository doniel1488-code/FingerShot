# AGENTS.md — FingerShot

## Назначение проекта

Разработай качественный Minecraft-мод **FingerShot** для **Minecraft Java 1.21.8 + Fabric**. Идея: игрок заряжает выстрел из пальца и выпускает мощный энергетический импульс. Это должна быть полноценная игровая способность с выразительной анимацией, визуальными и звуковыми эффектами, воздействием на сущности и настоящей визуализацией разрезания блоков.

Эта инструкция — основной набор требований проекта. Перед любыми изменениями прочитай её целиком, затем изучи фактическое состояние репозитория. Не считай перечисленные ниже функции уже реализованными: проверяй исходники и подтверждай выводы кодом, тестами и результатами сборки.

## 1. Сначала изучи репозиторий

1. Проверь текущую ветку, структуру проекта, историю коммитов, файлы Gradle, Fabric metadata, исходники, ресурсы и GitHub Actions.
2. Не перезаписывай и не удаляй существующую рабочую реализацию без необходимости. Сначала разберись, что уже сделано.
3. Если репозиторий ещё пустой, создай проект непосредственно в этом репозитории и в ветке `main`. Не создавай второй репозиторий и не ограничивайся локальным ZIP.
4. В начале работы кратко зафиксируй, что обнаружено: готово, отсутствует, сломано, что предстоит сделать. Затем переходи к реализации, не останавливаясь на одном аудите.

## 2. Техническая платформа

- Minecraft Java **1.21.8**.
- Fabric Loader и Fabric API, совместимые именно с Minecraft 1.21.8.
- Java **21**.
- Gradle Wrapper и Fabric Loom.
- Используй актуальные совместимые версии зависимостей, сверяясь с официальной документацией Fabric и репозиториями зависимостей. Не подставляй версии наугад.
- Задай уникальный mod id, например `fingershot`, корректные `fabric.mod.json`, entrypoints, зависимости и лицензионный файл.
- Проект должен собираться без IDE и локально установленных Gradle: сборка выполняется через Wrapper и GitHub Actions.
- Разделяй клиентскую и серверную части. Dedicated server не должен падать из-за загрузки клиентских классов, рендереров или key bindings.

## 3. Основная механика выстрела

Реализуй полноценный цикл способности:

1. Игрок удерживает назначенную клавишу — начинается зарядка.
2. Во время зарядки видны и слышны нарастающие эффекты: свечение пальца, энергия, частицы, электрические дуги и изменение звука.
3. При отпускании клавиши выполняется выстрел. Если заряд недостаточный, поведение должно быть понятно игроку и не вызывать случайных срабатываний.
4. После выстрела проигрываются анимация отдачи и восстановления, затем способность снова готова.
5. Предусмотри понятный индикатор заряда и состояния перезарядки. Он не должен закрывать важную часть интерфейса.

Анимация должна выглядеть именно как выстрел из пальца, а не как обычное нажатие кнопки или стандартный взмах рукой. Продумай положение кисти, пальца, локтя и корпуса. Сделай отдельные состояния: подготовка, зарядка, максимальный заряд, выстрел, отдача и восстановление.

## 4. Анимация от первого и третьего лица

- Реализуй заметную анимацию руки/пальца в первом лице.
- Реализуй соответствующее отображение способности в третьем лице, чтобы другие игроки видели зарядку и выстрел.
- Не ломай стандартные анимации ходьбы, бега, прыжка, плавания и использования предметов.
- Используй плавные переходы между состояниями, без резких телепортаций частей модели.
- Синхронизируй состояние способности с другими игроками через сетевые пакеты.
- Проверь работу с обычной правой и левой рукой, разными скинами и режимами перспективы.

## 5. Главное требование: настоящее визуальное разрезание блоков

**Не подменяй разрезание обычным разрушением блока с частицами.** При попадании луча блок должен выглядеть так, будто его физически рассекли на две части.

Минимально необходимое поведение:

1. Определи точку попадания и плоскость разреза. Направление и ориентация разреза должны зависеть от направления выстрела и точки попадания, а не быть одним и тем же эффектом для всех блоков.
2. Получи геометрию исходной модели блока и раздели её полигоны плоскостью разреза на две группы.
3. При разделении корректно интерполируй координаты вершин, UV-текстуры, цвет и необходимые данные вершин. Не растягивай текстуру и не допускай заметных дыр или мерцания.
4. Создай поверхность самого среза. Она должна быть визуально отличима: кратковременное яркое свечение, энергетическая кромка или материал, соответствующий эффекту способности.
5. Покажи две получившиеся части отдельно: они должны разойтись по разные стороны среза, получить небольшое вращение/инерцию и исчезнуть или перейти к понятному завершению эффекта.
6. Визуальный результат должен быть виден не только стрелявшему игроку, но и остальным участникам мира.
7. Обычные блоки с полной кубической геометрией (например, камень, булыжник, земля, доски) — обязательная первая группа для качественной поддержки.
8. Для сложных моделей, неполных блоков и нестандартных форм реализуй безопасную обработку либо явно документированный fallback. Не допускай вылета клиента из-за неподдерживаемой геометрии.
9. Не создавай бесконечные сущности-обломки и не оставляй невидимые коллизии после завершения эффекта.

Сервер должен авторитетно проверять попадание и решать, что происходит с блоком. Клиентская геометрия отвечает за красивую анимацию, но не может самостоятельно сообщать серверу, какой произвольный блок нужно удалить.

Продумай правила дропа: один корректный дроп, без дублирования предметов, без потери предметов из-за гонки пакетов и без повторного разрушения блока. Не разрушай блоки с BlockEntity (сундуки, печи и другие контейнеры) без отдельно реализованной и безопасной поддержки. Учитывай защиту территории и стандартные серверные проверки прав игрока.

Если полноценное геометрическое рассечение нельзя реализовать для конкретной модели, не выдавай обычное разрушение за успешный разрез. Покажи безопасный альтернативный эффект и укажи ограничение в документации.

## 6. Луч, попадания и воздействие

- Сделай заметный энергетический луч с глубиной и несколькими визуальными слоями, а не тонкую одноцветную линию.
- Добавь частицы, искры, электрические дуги, краткий импульс/вспышку в точке попадания и ударную волну.
- Учитывай расстояние, направление, препятствия и реальный raycast мира.
- Для разных материалов сделай различающиеся реакции: камень — каменная крошка и пыль, дерево — щепки и искры, земля — пыль и мелкие частицы. Не используй один и тот же набор частиц для всего.
- Реализуй воздействие на сущностей: урон, отбрасывание и визуальную реакцию. Значения должны быть настраиваемыми.
- Не допускай повторного нанесения урона одной цели одним выстрелом из-за нескольких клиентских/серверных событий.
- Добавь оригинальные звуковые ресурсы или корректно созданные звуковые события для зарядки, выстрела, попадания в блок, попадания в сущность и окончания эффекта. Проверь лицензии ресурсов.

## 7. Мультиплеер и безопасность

- Проверяй выстрел на сервере: игрок жив, способность доступна, заряд/перезарядка допустимы, дистанция и направление валидны.
- Не доверяй координатам цели и результатам raycast, присланным клиентом, без серверной перепроверки.
- Ограничь частоту пакетов и действий, чтобы исключить спам и простые эксплойты.
- Передавай другим игрокам необходимые события для синхронной анимации и визуальных эффектов.
- Убедись, что одиночная игра, LAN, выделенный сервер и несколько игроков работают без дублирования эффектов и дропа.
- Если выстрел невалиден или сервер отклоняет действие, клиент должен корректно сбросить локальное состояние зарядки.

## 8. Настройки

Добавь конфигурацию с безопасными значениями по умолчанию. Как минимум:

- максимальная дальность;
- время полной зарядки;
- время перезарядки;
- урон по сущностям;
- сила отбрасывания;
- разрешение/запрет воздействия на сущности;
- разрешение/запрет разрезания блоков;
- максимальное количество одновременно отображаемых частей/обломков;
- интенсивность визуальных эффектов;
- громкость звуков.

Проверь диапазоны значений и обработай некорректный конфиг. Настройки и их назначение опиши в README. Не добавляй параметры, которые на деле ни на что не влияют.

## 9. Качество кода и ресурсов

Раздели код по зонам ответственности: регистрация мода, способность и её состояния, обработка ввода, анимация, сетевой протокол, серверная валидация, raycast, геометрическое рассечение, рендеринг обломков, частицы, звуки и конфигурация.

Не помещай всю реализацию в один огромный класс. Не оставляй заглушки, пустые обработчики и TODO вместо обязательной механики. Избегай лишних зависимостей. Учитывай производительность: ограничивай количество частиц, обломков и активных эффектов; корректно удаляй временные объекты и освобождай ресурсы.

Создай README с описанием установки, управления, настроек, совместимости, ограничений геометрического разрезания и известных проблем. Добавь скриншоты или GIF реальной работы, когда сможешь получить их из фактического запуска игры. Не используй концепт-арт вместо доказательства работающей механики.

## 10. Проверки и критерии приёмки

Добавь GitHub Actions workflow, который запускается на push и pull request. Он должен:

- использовать Java 21;
- запускать Gradle Wrapper;
- проверять компиляцию и remap;
- запускать доступные автоматические тесты;
- собирать итоговый remapped Fabric JAR;
- публиковать JAR как GitHub Actions artifact.

Добавь тесты для геометрического разделения: пересечение полигона плоскостью, разделение куба, корректность вершин/UV, отсутствие пустой или некорректной геометрии. Добавь проверки логики зарядки, перезарядки, серверной валидации и однократного дропа там, где это возможно автоматизировать.

Одной успешной компиляции недостаточно, чтобы объявить механику готовой. По возможности запусти клиент и сервер либо автоматизированный smoke test. Проверь как минимум:

- зарядка и отпускание клавиши;
- анимация руки от первого лица;
- отображение выстрела и анимации в третьем лице;
- попадание луча в блок;
- видимое разделение блока на две части и свечение среза;
- отсутствие дублированного дропа;
- воздействие на сущность;
- синхронизация между двумя игроками;
- отсутствие ошибок в latest.log.

Для каждого непроверенного пункта прямо укажи, что именно не удалось проверить. Не пиши «полностью готово», если проверена только сборка.
